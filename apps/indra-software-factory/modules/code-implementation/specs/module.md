# Code implementation

**Prefix:** CIM

**Audience:** The people who run a project's flow from specs to code; whoever builds the skills of the plugin `code-implementation`

**Scope:** Layer 4: code built from the norms and the derived norms, within the acceptance units of layer 3, and its traceability to the acceptance units it implements and to the derived norms it is built from, and through them to their norms ([ACU-56](../../acceptance-management/specs/module.md#hashes-and-citations)). What every meta use case of the meta module does before it implements anything, which derived norms it reads and how the code cites them (CIM-11), and the hook of the session that keeps layer 4 from writing the acceptance repository (CIM-1), are here; how a task is implemented is in [implement.md](../use-cases/implement/specs/implement.md); what the five layers are and what layer 4 reads is in [layers.md](../../development-methodology/specs/layers.md); what an acceptance unit is, in [acceptance-management](../../acceptance-management/specs/module.md)

The meta module `code-implementation` of the meta app Indra Software Factory, listed in [app.md](../../../specs/app.md). The terms norm, norm ID, norm hash, derived norm, derived norm ID, derived norm fingerprint, code repository, norms repository and acceptance repository are those of [layers.md](../../development-methodology/specs/layers.md#terms); the terms citation, derived norm citation, run of code citations, derived norms of a commit, scope of an acceptance unit, acceptance unit behind layer 2, acceptance unit, unit ID, unit hash, acceptance architect, implementing agent and requester are those of [acceptance-management](../../acceptance-management/specs/module.md#terms); the terms list of derived norms, lines of a derived norm and types of derived norms of a commit are those of [norms-management](../../norms-management/specs/module.md#terms). In this meta spec, an acceptance unit behind layer 2 is one at the commit of the norms repository that ORC-25 reads; layer 4 does not implement it until the acceptance architect updates it ([ACU-41 and ACU-28](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event)).

## Terms

| Term | Meaning |
|---|---|
| User | The person who runs a meta use case of the meta module in the code repository, and confirms what it proposes. The user is not always the requester: a meta use case reports to the requester what [ACU-12](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence) says, and asks the user for every confirmation. |
| Comparison | The result of ORC-25 and CIM-9: the state of each citation of an acceptance unit and of each derived norm citation of the code repository. |
| Derived norms of the task | The derived norms that the `## Derived norms` of the acceptance unit of a task cites, each with its derived norm fingerprint and its lines in the commit of the norms repository that ORC-25 reads (CIM-11). |
| Review | What the meta use case shows from the comparison before it implements anything (ORC-26, CIM-2). It proposes nothing and decides nothing: what the meta use case implements is its task ([IMP-14](../use-cases/implement/specs/implement.md#implement-a-task)). |

## Implement the changed norms

- **ORC-25.** Every meta use case of the meta module reads the norms repository and the acceptance repository each at one commit, in the clone of each that [ORC-21](../../project-management/specs/module.md#where-the-repositories-are) finds. In a run ([ORC-15](../../development-methodology/specs/flow.md#start-a-run)), those commits are the hand-offs of the steps before: the commit of layer 2 of the run ([ORC-9](../../norms-management/specs/module.md#regenerate-the-norms)) and the hand-off of the step of layer 3 ([ACU-41](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event)); when a clone does not hold its commit, the meta use case implements nothing, and says which commit is missing. In a run, the orchestrator gives those commits in the prompt of the headless session of the step ([WFO-4](../../workflow-orchestration/specs/module.md#start-and-control-a-run)). Outside a run, each is the commit `HEAD` of its clone. Before it implements anything, it compares each citation of an acceptance unit of its own code repository with that commit of the acceptance repository, and each derived norm citation of it with that commit of the norms repository (CIM-9). A script makes the comparison, not the model, and computes each unit hash as [ACU-52](../../acceptance-management/specs/module.md#hashes-and-citations) says. Each citation of an acceptance unit gets one state (complete list); each derived norm citation gets the one of CIM-9:
  - `unchanged`: the file `units/<unit ID>.md` of its acceptance unit is in that commit, and its unit hash is the one of the citation;
  - `changed`: the file of its acceptance unit is in that commit, and its unit hash is another, or the file has no unit hash (ACU-52);
  - `retired`: the file of its acceptance unit is not in that commit, and the number of its unit ID is not greater than `last_unit_id` of `acceptance.json` in that commit: the acceptance unit was removed ([ACU-55](../../acceptance-management/specs/module.md#the-acceptance-area-and-the-acceptance-unit));
  - `unknown`: the number of its unit ID is greater than `last_unit_id`: no acceptance unit ever had that unit ID.

  Rationale: layer 4 implements what layers 2 and 3 handed off, so it reads the very commits of their hand-offs, not whatever the clones hold; reading both repositories at fixed commits makes every unit hash and every derived norm fingerprint that it compares with come from one version of each. A citation names the version of what it cites by its hash ([LAY-12](../../development-methodology/specs/layers.md#rules)), so comparing each citation of an acceptance unit and each derived norm citation with those commits shows which code a change of an acceptance unit, of a derived norm or of a norm reaches. A script computes it, so that the comparison is the same each time and the model cannot miss a citation.
- **ORC-26.** From the comparison, the meta use case shows a review before it implements anything. The review lists (complete list): every citation of an acceptance unit `changed`, `retired` or `unknown`, each with the files that hold it and what CIM-2 says of it; every derived norm citation `changed`, `retired` or `unknown` (CIM-9), each with the files that hold it and what CIM-10 says of it; and every acceptance unit cited by a citation `unchanged` that is an acceptance unit behind layer 2, with the norms and the derived norms that make it so. It lists no other acceptance unit, and it does not say which acceptance units the code repository implements: those come from the plan of implementation ([ACU-39](../../acceptance-management/specs/module.md#the-plan-of-implementation)), and the norms of each from its `## Norms` ([ACU-8](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository)). A citation of the review whose acceptance unit is not the task stays as it is ([IMP-9](../use-cases/implement/specs/implement.md#implement-a-task)). Rationale: the review shows the implementing agent, before it writes anything, exactly the code that is stale, whether through a citation of an acceptance unit or through a derived norm citation, and the acceptance units it must not implement yet because they are behind layer 2, with the norms and the derived norms that make them so; a citation `unchanged` of an acceptance unit that is not behind layer 2 needs nothing, so listing it would only hide what does.
- **CIM-2.** For each citation of an acceptance unit that the review of ORC-26 lists, the review names, from the commit of the acceptance repository that ORC-25 reads (complete list):
  - for a citation `changed`: the title of its acceptance unit; whether its acceptance unit is an acceptance unit behind layer 2, and, when it is, the norms and the derived norms that make it so; and the diff of the range of ACU-52 of the file of the acceptance unit, from the latest ancestor of that commit whose file of the acceptance unit has the unit hash of the citation, to that commit, or, when no ancestor has it, that no version of the acceptance unit with that unit hash is found;
  - for a citation `retired`: that its acceptance unit was removed, with the latest commit, that commit or one of its ancestors, that removed the file of the acceptance unit;
  - for a citation `unknown`: that no acceptance unit had that unit ID.

  A script computes all of it, not the model. Code that cites an acceptance unit behind layer 2 is never changed by a meta use case of the meta module, because layer 4 builds code only within the acceptance units of layer 3 as they stand ([LAY-4](../../development-methodology/specs/layers.md#rules)): the acceptance architect updates the acceptance unit first ([ACU-28](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event)).

  Rationale: the state alone says that the code is stale, not what to change in it; the diff of the acceptance unit, and the norms and the derived norms that put it behind layer 2, show the implementing agent what the code must now do, or why it must wait for layer 3, as CIM-10 does for a derived norm. A script computes it so that the review is the same each time and the model cannot miss a change.
- **ORC-27.** When the comparison cannot run, the meta use case implements nothing, and says why. One case in which the comparison cannot run is when the derived norms of the commit of the norms repository cannot be read ([ACU-78](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository)). Rationale: without the comparison, the meta use case cannot tell stale code from code that is current, nor whether its task is behind layer 2, so anything it implemented could be built on an old version of an acceptance unit or of a derived norm; with the derived norms unreadable, neither the derived norm citations nor the derived norms of the task can be read (CIM-9, CIM-11).
- **CIM-9.** A derived norm citation of the code repository is a derived norm citation of [ACU-56](../../acceptance-management/specs/module.md#hashes-and-citations) after a comment mark, in a file of the code repository. Each one gets one state, from the derived norms of the commit of the norms repository that ORC-25 reads ([ACU-78](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository)) (complete list):
  - `unchanged`: that commit holds its derived norm, with the derived norm fingerprint of the citation;
  - `changed`: that commit holds its derived norm, with another derived norm fingerprint;
  - `retired`: that commit does not hold its derived norm, and its number is not greater than `last_derived_norm_number` of the list of derived norms of its type in the latest commit, that commit or one of its ancestors, whose types of derived norms hold the type of its derived norm ID, as the types of derived norms of a commit say ([NRM-16](../../norms-management/specs/module.md#derive-the-derived-norms)): the derived norm was removed, alone or with its whole type ([NRM-13](../../norms-management/specs/module.md#the-list-of-derived-norms)). It is the state that [ACU-62](../../acceptance-management/use-cases/define/specs/define.md#define-the-acceptance-areas-and-acceptance-units) gives the same derived norm citation in an acceptance unit;
  - `unknown`: otherwise: no list of derived norms of that commit or of one of its ancestors gave that derived norm ID, because its number is greater than `last_derived_norm_number` of that latest commit, or because no such commit exists, as for a type that the types of derived norms of no commit ever held.

  A script makes it, not the model, from the lists of derived norms ([NRM-12](../../norms-management/specs/module.md#the-list-of-derived-norms)); it computes no derived norm fingerprint.

  Rationale: a derived norm citation names the version of the derived norm that its code was built from; comparing it with the derived norms of the commit that layer 4 reads shows which code a change of a derived norm, or of a norm it cites, reaches ([LAY-12](../../development-methodology/specs/layers.md#rules)). `last_derived_norm_number` tells a derived norm that was removed, whose code must go, from an ID that never existed, which is an error of the citation, as `last_unit_id` does for the citations of an acceptance unit (ORC-25). When its type is no longer one of the types of derived norms of the commit, its list no longer counts, so the script reads `last_derived_norm_number` from the latest commit whose types of derived norms still held the type: the derived norm ID of a derived norm removed with its type was once given, so the citation is `retired`, as in layer 3, and not `unknown`. The derived norm fingerprints come from the lists alone, since only the script of the generator computes them ([NRM-15](../../norms-management/specs/module.md#the-list-of-derived-norms)).
- **CIM-10.** For each derived norm citation that the review of ORC-26 lists, the review names, from the commit of the norms repository that ORC-25 reads (complete list):
  - for a citation `changed`: the name of its derived norm; the norm ID and the norm hash of each norm that it cites in that commit and that it did not cite, or cited with another norm hash, in the version of the citation; and the diff of the lines of the derived norm, from the latest ancestor of that commit whose list of derived norms gives the derived norm the derived norm fingerprint of the citation, to that commit, or, when no ancestor has it, that no version of the derived norm with that derived norm fingerprint is found;
  - for a citation `retired`: that its derived norm was removed, with the latest commit, that commit or one of its ancestors, whose derived norms of a commit dropped it, either because its list of derived norms no longer held it or because the types of derived norms of that commit no longer held its type;
  - for a citation `unknown`: that no derived norm had that derived norm ID.

  A script computes all of it, not the model. A derived norm citation of the review whose code does not serve the task stays as it is, as a citation of an acceptance unit that is not the task does ([IMP-9](../use-cases/implement/specs/implement.md#implement-a-task)).

  Rationale: the state alone says that the code is stale, not what to change in it; the norms that changed and the diff of the lines of the derived norm show the implementing agent exactly what of the derived norm the code must now follow, as CIM-2 does for an acceptance unit. A script computes it so that the review is the same each time and the model cannot miss a change.

## The derived norms of the code

- **CIM-11.** Layer 4 reads and cites the derived norms of an acceptance unit as follows ([LAY-4](../../development-methodology/specs/layers.md#rules)):
  - Before it implements a task, a meta use case of the meta module reads the derived norms of the task: for each derived norm citation of the `## Derived norms` of the acceptance unit of the task, the line of its derived norm in the list of derived norms of the commit of the norms repository that ORC-25 reads, and the lines of that derived norm in that commit. A script finds them, not the model. A meta use case of the meta module implements a task only when it is not an acceptance unit behind layer 2 at that commit ([ACU-41](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event)), so the derived norm fingerprint of each of them in that commit is the one that `## Derived norms` cites.
  - It reads no other derived norm to implement the task: the derived norms that the task needs are those of its scope ([ACU-78](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository)), which `## Derived norms` cites.
  - The code and the unit tests that it builds from a derived norm of the task carry a derived norm citation of it, in the form of [ACU-56](../../acceptance-management/specs/module.md#hashes-and-citations), with the derived norm fingerprint that `## Derived norms` of the task cites, in the same run of code citations as the citation of the task, and placed as that citation is. Code built from no derived norm carries no derived norm citation.
  - Before it reports the task as done, a script checks every derived norm citation that the meta use case wrote: its derived norm ID is cited by `## Derived norms` of an acceptance unit that the same run of code citations cites, with the same derived norm fingerprint, which is the derived norm fingerprint of its derived norm in that commit of the norms repository.

  Rationale: a derived norm is built for the agent that implements, as a grammar or a semantics that says exactly what the norms say ([LAY-3](../../development-methodology/specs/layers.md#rules)); the code that follows it cites it, so that a new derived norm fingerprint, from a change of the derived norm or of a norm it cites, shows layer 4 exactly which code to review (CIM-9, [LAY-12](../../development-methodology/specs/layers.md#rules)).

## The hook of the session

- **CIM-1.** The plugin declares in its file `hooks/hooks.json` one hook on the event `PreToolUse`, for these tools (complete list): `Edit`, `Write`, `NotebookEdit` and `Bash`. Each time it runs, the hook finds the repository of the session and the project folder as [ACU-45](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence) says, and takes as the path of the acceptance repository the project folder followed by the `path` of the entry of layer 3 of the `project.json` of the repository of the session, with its symbolic links followed. It resolves `file_path` and `notebook_path` as [ACU-45](../../acceptance-management/specs/module.md) resolves a path. It refuses every call of `Edit` or `Write` whose `file_path`, and every call of `NotebookEdit` whose `notebook_path`, is inside the acceptance repository, and every call of `Bash` that may write a file of it as CIM-7 says ([ACU-13](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence), level 1). Reading the acceptance repository is allowed: the implementing agent reads it and runs its tests ([LAY-4](../../development-methodology/specs/layers.md#rules)). Rationale: a shell command can write a path in more ways than a hook recognises, so the hook guards against mistakes; levels 2 and 3 of [ACU-13](../../acceptance-management/specs/module.md) are the barrier.
- **CIM-3.** The hook splits a command of `Bash` into its simple commands, at `;`, `&&`, `||`, `|`, `&`, parentheses and new lines, and each simple command into its words, as a POSIX shell splits it, with quotes removed. The current directory of a simple command is the field `cwd` of the call, changed by each earlier simple command `cd` or `pushd` of the call to its first word after the program name that is not an option, resolved as CIM-1 says against the current directory of that earlier command, or to the home directory when it has no such word. An option is a word that starts with `-` and is not `-` itself, before a word `--`, if any; `--` is not that first word. When that first word is `-`, as in `cd -` and `pushd -`, the current directory stays unchanged.
- **CIM-6.** The name of the acceptance repository is the last part of the `path` of the entry of layer 3 ([ORC-20](../../project-management/specs/module.md#where-the-repositories-are)), and also the last part of its real path (CIM-1) when that differs. A simple command of CIM-3 names the acceptance repository in each of these cases (complete list):
  1. one of its words that holds neither `$` nor a backquote, resolved as CIM-1 says against its current directory, is a path inside the acceptance repository; a word that starts with `-` and holds `=` is taken as the part after its first `=`;
  2. one of its words holds `$` or a backquote, and one of the parts of that word between `/`, quotes, `$`, braces, parentheses, backquotes and blanks is a name of the acceptance repository;
  3. its current directory is inside the acceptance repository;
  4. it starts with `xargs` or `parallel`, and any earlier simple command of the call, not only the one before it in a pipe, names the acceptance repository.

  A command that cannot be split into words, or that holds a command substitution, names the acceptance repository when its text holds a name of the acceptance repository, or when the field `cwd` of the call is inside it.
- **CIM-7.** The hook refuses a call of `Bash`, with the reason that follows, in each of these cases (complete list), where naming the acceptance repository is as CIM-6 says:
  1. the command names the acceptance repository and cannot be split into words: `it names the acceptance repository and cannot be read as a shell command`;
  2. the command names the acceptance repository and holds a command substitution, `$(` or a backquote: `it names the acceptance repository and runs a command substitution`;
  3. a simple command that names the acceptance repository is not a command that only reads (CIM-8): `the command '<simple command>' may write it`, where `<simple command>` is its words joined by single blanks.
- **CIM-8.** A simple command only reads when it redirects no output, with `>`, `>>`, `>|`, `>&`, `&>`, `&>>`, `<>` or `<n>>`, to a path inside the acceptance repository, and its program, after the assignments of variables before it, is one of these (complete list):
  - `cat`, `head`, `tail`, `more`, `ls`, `grep`, `egrep`, `fgrep`, `wc`, `diff`, `cmp`, `stat`, `du`, `realpath`, `readlink`, `basename`, `dirname`, `pwd`, `echo`, `printf`, `test`, `[`, `true`, `false`, `jq`, `md5`, `md5sum`, `shasum`, `sha1sum`, `sha256sum`, `cd`, `pushd`, `popd`, with any option;
  - `less` without `-o`, `-O`, `--log-file` or `--LOG-FILE`; `tree` without `-o`; `rg` without `--pre`; `file` without `-C`;
  - `find` without `-delete`, `-exec`, `-execdir`, `-ok`, `-okdir`, `-fprint`, `-fprint0`, `-fprintf` or `-fls`;
  - `cp` whose destination, the value of `-t` or `--target-directory` when it has one, or else its last word that is not an option, is outside the acceptance repository; `rsync` whose destination, its last word that is not an option, is outside the acceptance repository, without an option that starts with `--delete` or `--remove-source` (for `rsync`, `-t` keeps the times and names no destination);
  - `git` without the global options `-c` or `--config-env`, with one of the subcommands `log`, `show`, `diff`, `status`, `rev-parse`, `ls-files`, `ls-tree`, `cat-file`, `archive`, `clone`, `describe`, `blame`, `grep`, `shortlog`, `rev-list`, `for-each-ref`, `show-ref`; without `--output` to a path inside the acceptance repository, nor `-o` for `archive`; `grep` without `-O` or `--open-files-in-pager`; and `clone` whose destination is outside the acceptance repository: its second word that is neither an option nor the value of one, or, when it has none, the folder that `git clone` creates in the working directory, named after the last part of the repository's URL without `.git`.

  Example (illustrative): `--output=../acceptance/report.txt` is taken as `../acceptance/report.txt`; a command with a quote that is not closed cannot be split into words.

  So a copy of the acceptance repository made outside it, as [IMP-16](../use-cases/implement/specs/implement.md#implement-a-task) asks, with `git clone`, `git archive`, `cp` or `rsync`, is allowed.
- **CIM-4.** The hook of CIM-1 refuses a call with the JSON object of [ACU-38](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence), on its standard output, and ends with status 0; when it refuses nothing, it prints nothing and ends with status 0. The reason of a refusal is, word for word: `A session of layer 4 never writes the acceptance repository <path> (CIM-1, [LAY-4](../../development-methodology/specs/layers.md#rules)): <why>. Reading it is allowed; run its acceptance tests in a copy made outside it ([IMP-16](../use-cases/implement/specs/implement.md)).`, where `<path>` is the real path of the acceptance repository and `<why>` is `<file path> is a file of it` for `Edit`, `Write` and `NotebookEdit`, where `<file path>` is the field as the call gives it, or the reason of the case of CIM-7 for `Bash`.
- **CIM-5.** The hook of CIM-1 refuses nothing when it cannot find the path of the acceptance repository, which happens in these cases (complete list): the cases of [ACU-40](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence) for the repository of the session and its own entry; `project.json` does not hold exactly one entry of layer 3; the `path` of that entry is not valid ([ORC-20](../../project-management/specs/module.md#where-the-repositories-are)). It also refuses nothing when its input is not a JSON object, and when it fails in any other way. Rationale: a hook that refused every call in a repository it cannot read would stop a session that is not of a project.
