# Code implementation

**Prefix:** CIM

**Audience:** The people who run a project's flow from specs to code; whoever builds the skills of the plugin `code-implementation`

**Scope:** Layer 4: code built from the norms and the derived norms, within the acceptance units of layer 3, and its traceability to the acceptance units it implements, and through them to their norms ([ACU-56](../../acceptance-management/specs/module.md#hashes-and-citations)). What every use case of the module does before it implements anything, and the hook of the session that keeps layer 4 from writing the acceptance repository (CIM-1), are here; how a task is implemented is in [implement.md](../use-cases/implement/specs/implement.md); what the five layers are and what layer 4 reads is in [layers.md](../../development-methodology/specs/layers.md); what an acceptance unit is, in [acceptance-management](../../acceptance-management/specs/module.md)

The module `code-implementation` of the app Indra Software Factory, listed in [app.md](../../../specs/app.md). The terms norm, norm ID, norm hash, code repository, norms repository and acceptance repository are those of [layers.md](../../development-methodology/specs/layers.md#terms); the terms citation, acceptance unit, unit ID, unit hash and requester are those of [acceptance-management](../../acceptance-management/specs/module.md#terms).

## Terms

| Term | Meaning |
|---|---|

The user is not always the requester: a use case reports to the requester what [ACU-12](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence) says, and asks the user for every confirmation. |
| Comparison | The result of ORC-25: the state of each citation of the code repository. |
| Acceptance unit behind layer 2 | An acceptance unit whose `## Norms` cites a norm with a norm hash other than its norm hash in the commit of the norms repository that ORC-25 reads, or a norm that commit does not hold. Layer 4 does not implement it until the acceptance architect updates it ([ACU-41](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event), [ACU-28](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event)). |
| Review | What the use case shows from the comparison before it implements anything (ORC-26, CIM-2). It proposes nothing and decides nothing: what the use case implements is its task ([IMP-14](../use-cases/implement/specs/implement.md#implement-a-task)). |

## Implement the changed norms

- **ORC-25.** Every use case of the module reads the norms repository and the acceptance repository each at one commit, in the clone of each that [ORC-21](../../project-management/specs/module.md#where-the-repositories-are) finds. In a run ([ORC-15](../../development-methodology/specs/flow.md#start-a-run)), those commits are the hand-offs of the steps before: the commit of layer 2 of the run ([ORC-9](../../norms-management/specs/module.md#regenerate-the-norms)) and the hand-off of the step of layer 3 ([ACU-41](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event)); when a clone does not hold its commit, the use case implements nothing, and says which commit is missing. In a run, the orchestrator gives those commits in the prompt of the headless session of the step ([WFO-4](../../workflow-orchestration/specs/module.md#start-and-control-a-run)). Outside a run, each is the commit `HEAD` of its clone. Before it implements anything, it compares each citation of its own code repository with that commit of the acceptance repository. A script makes the comparison, not the model, and computes each unit hash as [ACU-52](../../acceptance-management/specs/module.md#hashes-and-citations) says. Each citation gets one state (complete list):
  - `unchanged`: the file `units/<unit ID>.md` of its acceptance unit is in that commit, and its unit hash is the one of the citation;
  - `changed`: the file of its acceptance unit is in that commit, and its unit hash is another, or the file has no unit hash (ACU-52);
  - `retired`: the file of its acceptance unit is not in that commit, and the number of its unit ID is not greater than `last_unit_id` of `acceptance.json` in that commit: the acceptance unit was removed ([ACU-55](../../acceptance-management/specs/module.md#the-acceptance-area-and-the-acceptance-unit));
  - `unknown`: the number of its unit ID is greater than `last_unit_id`: no acceptance unit ever had that unit ID.
- **ORC-26.** From the comparison, the use case shows a review before it implements anything. The review lists (complete list): every citation `changed`, `retired` or `unknown`, each with the files that hold it and what CIM-2 says of it; and every acceptance unit cited by a citation `unchanged` that is an acceptance unit behind layer 2, with the norms that make it so. It lists no other acceptance unit, and it does not say which acceptance units the code repository implements: those come from the plan of implementation ([ACU-39](../../acceptance-management/specs/module.md#the-plan-of-implementation)), and the norms of each from its `## Norms` ([ACU-8](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository)). A citation of the review whose acceptance unit is not the task stays as it is ([IMP-9](../use-cases/implement/specs/implement.md#implement-a-task)).
- **CIM-2.** For each citation that the review of ORC-26 lists, the review names, from the commit of the acceptance repository that ORC-25 reads (complete list):
  - for a citation `changed`: the title of its acceptance unit; whether its acceptance unit is an acceptance unit behind layer 2, and, when it is, the norms that make it so; and the diff of the range of ACU-52 of the file of the acceptance unit, from the latest ancestor of that commit whose file of the acceptance unit has the unit hash of the citation, to that commit, or, when no ancestor has it, that no version of the acceptance unit with that unit hash is found;
  - for a citation `retired`: that its acceptance unit was removed, with the latest commit, that commit or one of its ancestors, that removed the file of the acceptance unit;
  - for a citation `unknown`: that no acceptance unit had that unit ID.

  A script computes all of it, not the model. Code that cites an acceptance unit behind layer 2 is never changed by a use case of the module, because layer 4 builds code only within the acceptance units of layer 3 as they stand ([LAY-4](../../development-methodology/specs/layers.md#rules)): the acceptance architect updates the acceptance unit first ([ACU-28](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event)).
- **ORC-27.** When the comparison cannot run, the use case implements nothing, and says why.

## The hook of the session

- **CIM-1.** The plugin declares in its file `hooks/hooks.json` one hook on the event `PreToolUse`, for these tools (complete list): `Edit`, `Write`, `NotebookEdit` and `Bash`. Each time it runs, the hook finds the repository of the session and the project folder as [ACU-45](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence) says, and takes as the path of the acceptance repository the project folder followed by the `path` of the entry of layer 3 of the `project.json` of the repository of the session, with its symbolic links followed. It resolves `file_path` and `notebook_path` as [ACU-45](../../acceptance-management/specs/module.md) resolves a path. It refuses every call of `Edit` or `Write` whose `file_path`, and every call of `NotebookEdit` whose `notebook_path`, is inside the acceptance repository, and every call of `Bash` that may write a file of it as CIM-7 says ([ACU-13](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence), level 1). Reading the acceptance repository is allowed: the implementing agent reads it and runs its tests ([LAY-4](../../development-methodology/specs/layers.md#rules)). Rationale: a shell command can write a path in more ways than a hook recognises, so the hook guards against mistakes; levels 2 and 3 of [ACU-13](../../acceptance-management/specs/module.md) are the barrier.
- **CIM-3.** The hook splits a command of `Bash` into its simple commands, at `;`, `&&`, `||`, `|`, `&`, parentheses and new lines, and each simple command into its words, as a POSIX shell splits it, with quotes removed. The current directory of a simple command is the field `cwd` of the call, changed by each earlier simple command `cd` or `pushd` of the call to its first word after the program name that is not an option, resolved as CIM-1 says against the current directory of that earlier command, or to the home directory when it has no such word. An option is a word that starts with `-` and is not `-` itself, before a word `--`, if any; `--` is not that first word. When that first word is `-`, as in `cd -` and `pushd -`, the current directory stays unchanged.
- **CIM-6.** The name of the acceptance repository is the last part of the `path` of the entry of layer 3 ([ORC-20](../../project-management/specs/module.md#where-the-repositories-are)), and also the last part of its real path (CIM-1) when that differs. A simple command of CIM-3 names the acceptance repository in each of these cases (complete list):
  1. one of its words that holds neither `$` nor a backquote, resolved as CIM-1 says against its current directory, is a path inside the acceptance repository; a word that starts with `-` and holds `=` is taken as the part after its first `=`;
  2. one of its words holds `$` or a backquote, and one of the parts of that word between `/`, quotes, `$`, braces, parentheses, backquotes and blanks is a name of the acceptance repository;
  3. its current directory is inside the acceptance repository;
  4. it starts with `xargs` or `parallel`, and any earlier simple command of the call, not only the one before it in a pipe, names the acceptance repository.

  A command that cannot be split into words, or that holds a command substitution, names the acceptance repository when its text holds a name of the acceptance repository, or when the field `cwd` of the call is inside it.
- **CIM-7.** The hook refuses a call of `Bash`, with the reason that follows, in each of these cases (complete list), where naming the acceptance repository is as CIM-6 says:
  1. the command names the acceptance repository and cannot be split into words: `it names the acceptance repository and cannot be read as a shell command`;
  2. the command names the acceptance repository and holds a command substitution, `$(` or a backquote: `it names the acceptance repository and runs a command substitution`;
  3. a simple command that names the acceptance repository is not a command that only reads (CIM-8): `the command '<simple command>' may write it`, where `<simple command>` is its words joined by single blanks.
- **CIM-8.** A simple command only reads when it redirects no output, with `>`, `>>`, `>|`, `>&`, `&>`, `&>>`, `<>` or `<n>>`, to a path inside the acceptance repository, and its program, after the assignments of variables before it, is one of these (complete list):
  - `cat`, `head`, `tail`, `more`, `ls`, `grep`, `egrep`, `fgrep`, `wc`, `diff`, `cmp`, `stat`, `du`, `realpath`, `readlink`, `basename`, `dirname`, `pwd`, `echo`, `printf`, `test`, `[`, `true`, `false`, `jq`, `md5`, `md5sum`, `shasum`, `sha1sum`, `sha256sum`, `cd`, `pushd`, `popd`, with any option;
  - `less` without `-o`, `-O`, `--log-file` or `--LOG-FILE`; `tree` without `-o`; `rg` without `--pre`; `file` without `-C`;
  - `find` without `-delete`, `-exec`, `-execdir`, `-ok`, `-okdir`, `-fprint`, `-fprint0`, `-fprintf` or `-fls`;
  - `cp` whose destination, the value of `-t` or `--target-directory` when it has one, or else its last word that is not an option, is outside the acceptance repository; `rsync` whose destination, its last word that is not an option, is outside the acceptance repository, without an option that starts with `--delete` or `--remove-source` (for `rsync`, `-t` keeps the times and names no destination);
  - `git` without the global options `-c` or `--config-env`, with one of the subcommands `log`, `show`, `diff`, `status`, `rev-parse`, `ls-files`, `ls-tree`, `cat-file`, `archive`, `clone`, `describe`, `blame`, `grep`, `shortlog`, `rev-list`, `for-each-ref`, `show-ref`; without `--output` to a path inside the acceptance repository, nor `-o` for `archive`; `grep` without `-O` or `--open-files-in-pager`; and `clone` whose destination is outside the acceptance repository: its second word that is neither an option nor the value of one, or, when it has none, the folder that `git clone` creates in the working directory, named after the last part of the repository's URL without `.git`.

  Example (illustrative): `--output=../acceptance/report.txt` is taken as `../acceptance/report.txt`; a command with a quote that is not closed cannot be split into words.

  So a copy of the acceptance repository made outside it, as [IMP-16](../use-cases/implement/specs/implement.md#implement-a-task) asks, with `git clone`, `git archive`, `cp` or `rsync`, is allowed.
- **CIM-4.** The hook of CIM-1 refuses a call with the JSON object of [ACU-38](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence), on its standard output, and ends with status 0; when it refuses nothing, it prints nothing and ends with status 0. The reason of a refusal is, word for word: `A session of layer 4 never writes the acceptance repository <path> (CIM-1, [LAY-4](../../development-methodology/specs/layers.md#rules)): <why>. Reading it is allowed; run its acceptance tests in a copy made outside it ([IMP-16](../use-cases/implement/specs/implement.md)).`, where `<path>` is the real path of the acceptance repository and `<why>` is `<file path> is a file of it` for `Edit`, `Write` and `NotebookEdit`, where `<file path>` is the field as the call gives it, or the reason of the case of CIM-7 for `Bash`.
- **CIM-5.** The hook of CIM-1 refuses nothing when it cannot find the path of the acceptance repository, which happens in these cases (complete list): the cases of [ACU-40](../../acceptance-management/specs/module.md#acceptance-tests-and-independent-evidence) for the repository of the session and its own entry; `project.json` does not hold exactly one entry of layer 3; the `path` of that entry is not valid ([ORC-20](../../project-management/specs/module.md#where-the-repositories-are)). It also refuses nothing when its input is not a JSON object, and when it fails in any other way. Rationale: a hook that refused every call in a repository it cannot read would stop a session that is not of a project.
