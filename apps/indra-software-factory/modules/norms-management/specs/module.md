# Norms management

**Prefix:** NRM

**Audience:** The people who run a project's flow from specs to code; whoever builds the skills of the plugin `norms-management`; whoever builds the generator of a type of derived norms

**Scope:** Layer 2: the norms and the derived norms. What each type of derived norms derives, and how, is in the spec of its generator

The module `norms-management` of the app Indra Software Factory, listed in [app.md](../../../specs/app.md). The terms norm, norm ID, norm hash, norms repository, derived norm, derived norm ID and derived norm fingerprint are those of [layers.md](../../development-methodology/specs/layers.md#terms), and the terms norm citation and scope of an acceptance unit are those of [acceptance-management](../../acceptance-management/specs/module.md#terms).

## Terms

| Term | Meaning |
|---|---|
| Run | One pass of the flow from specs to code, for one commit of layer 1. |
| Step | The work of one layer in one run, done in the repository of that layer. |
| Hand-off | What a step gives the next one: a commit, a report, or an issue. |
| Commit of layer 2 of the run | The commit that the step of layer 2 made (NRM-9), or, when the step made no commit, the head of the default branch of the repository of layer 2 from before the step. Never the merge commit, nor a commit brought, of the pull of NRM-10 that the step itself made. |
| Commit of a step | A commit with one parent, or none, that changes a file of `data/`, `specs-repo-annotated/` or `specs-derived/` against its first parent, or holds one when it has no parent: a commit that a step of layer 2 made (NRM-9). A merge commit is never one. |
| Last commit of a step | The first commit of a step met when walking the first parents from the commit of layer 2 of the run, that commit included. None when the walk meets none. |
| Commit before the last step | The first parent of the last commit of a step. None when there is no last commit of a step, or it has no parent. |
| Record of the types of derived norms | The file `specs-derived/types-of-derived-norms.json` that the step of layer 2 writes: the types of `derived_norms` whose derived-norms generators it ran, in their order (NRM-16). |
| Types of derived norms of a commit | The types of its record of the types of derived norms, when it holds one that meets NRM-16, and otherwise those of `derived_norms` of its `project.json` (NRM-1), in their order. |
| Norms generator | The program of this plugin that `/norms-management:build` and `/norms-management:verify` run, which writes `data/` and `specs-repo-annotated/`. |
| Derived-norms generator | The use case that a `derived_norms` entry of `project.json` names for one type ([ORC-20](../../project-management/specs/module.md#where-the-repositories-are)): a use case of a plugin that the project installs in its repository of layer 2. |
| Output of a type | Every file under `specs-derived/<type>/` of the repository of layer 2. |
| Status file | The one file of the output of a type, named by the spec of its derived-norms generator, that records how the output was made and the state of each item it derives. |
| Pending item | An item of the output of a type that the norms leave open ([LAY-5](../../development-methodology/specs/layers.md#rules)). |
| Acceptance unit | The smallest part of the product that the requester can recognise and validate end to end, as [acceptance-management](../../acceptance-management/specs/module.md#terms) defines it: what layer 3 writes, and what cites the derived norms of the scope of an acceptance unit ([ACU-78](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository)). |
| Orchestrator | The skills, the scripts and the hook of the plugin `workflow-orchestration`, in a session of the orchestration repository, as [workflow-orchestration](../../workflow-orchestration/specs/module.md#terms) defines it: what starts and controls a run, and decides ORC-10. |
| List of derived norms | The file `specs-derived/<type>/derived-norms.jsonl` of the output of a type: its derived norms, each with its derived norm ID, its derived norm fingerprint, where it is and the norms it cites (NRM-12). |
| Lines of a derived norm | The lines of the file of the output that holds a derived norm, from its `first_line` to its `last_line` in the list of derived norms, its citation lines included (NRM-12). |
| Citation line | A line of a derived norm that is one of its norm citations ([LAY-3](../../development-methodology/specs/layers.md#rules)), in the form that the spec of its derived-norms generator gives (NRM-15). |
| Content of a derived norm | Its lines without its citation lines, as NRM-14 takes them: what the derived norm itself contributes. |
| Derived norm behind its norms | A derived norm of a list of derived norms that cites, in its `cited_norms`, a norm ID that is the `id` of no active node of `data/tree.jsonl` of the same commit, a line of `type` `node` whose `status` is `active` or absent ([R61](norms-versions.md#data-and-outputs)), so also the norm ID of a retired node, or a norm with a norm hash that is not the norm hash of that norm there (NRM-11, rule 5): one whose derived-norms generator did not update it after a norm it cites changed or was retired. |
| List before the run | The list of derived norms of a type as the head of the default branch of the repository of layer 2 holds it when the step of layer 2 starts: the one that the step committed last (NRM-9), read from the history of the repository, never from the working tree. None when that head does not hold it, or the repository has no commit yet. |

## Regenerate the norms

- **ORC-34.** The skills of the module find the repository of layer 1 only through `project.json`, as [ORC-21 and ORC-22](../../project-management/specs/module.md#where-the-repositories-are) say, and the repository they run in must be the one of layer 2. There is no other way: no argument, no `CLAUDE.md`, no folder name.
- **ORC-8.** In the repository of layer 2, the step runs `/norms-management:build` at the commit of layer 1 that starts the run ([ORC-15](../../development-methodology/specs/flow.md#start-a-run)), then `/norms-management:verify`. A failure of either ends the run, with the norms generator's message shown as it is ([LAY-3](../../development-methodology/specs/layers.md#rules)).
- **ORC-9.** Its hand-off is the commit of layer 2 of the run, which holds the regenerated `data/`, `specs-repo-annotated/` and `specs-derived/` (NRM-9), and its `data/report.md`, which lists by norm ID what changed, together with the report of NRM-11, which lists by derived norm ID the derived norms that changed. Rationale: layers 3 and 4 read the norms and the derived norms at one fixed commit, and the two reports tell them by ID what changed there; without the report of NRM-11, a derived norm that changed while no norm changed would reach no acceptance unit and no code that cites it ([LAY-12](../../development-methodology/specs/layers.md#rules)).
- **ORC-10.** After this step, the run goes on with layers 3 and 4, ends or stops, by the first case that holds (complete list):
  1. when the report of NRM-11 shows a list of derived norms that cannot be read at the commit of layer 2 of the run, a derived norm behind its norms among them (NRM-11, rule 5), or no comparison (NRM-11, rule 2), the run stops: layer 3 could not read the derived norms that it cites ([ACU-78](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository)), or would cite a derived norm behind its norms with a derived norm fingerprint that did not change with its norms, and neither layer 3 nor layer 4 would see that it is stale ([LAY-12](../../development-methodology/specs/layers.md#rules));
  2. when `data/report.md` shows no change of norm and the report of NRM-11 shows no change of a derived norm and no change of the order of the types, the run ends: layers 3 and 4 have nothing to do;
  3. otherwise, layers 3 and 4 follow.

  The orchestrator decides which with a script of its own, by the rules of NRM-11 ([WFO-13](../../workflow-orchestration/specs/module.md#start-and-control-a-run)). Rationale: a new version of a derived-norms generator may change a derived norm while no norm changed ([LAY-6](../../development-methodology/specs/layers.md#rules), [LAY-12](../../development-methodology/specs/layers.md#rules)), and the acceptance units and the code that cite it must then be updated.

## Derive the derived norms

A project may have derived norms of zero or more types; a grammar and a
semantics are two of them in the examples of this spec ([LAY-3](../../development-methodology/specs/layers.md#rules)). Each
type has its own derived-norms generator. The clauses below are the interface
that every derived-norms generator follows, whatever it derives.

- **NRM-1.** The types of derived norms of a project are the `type` of each entry of `derived_norms` in its `project.json`, in their order: each entry names one type and the use case of its derived-norms generator. A project without `derived_norms` has no type of derived norms, and so no derived norm. Every script that reads a `project.json` for NRM-11 or NRM-16 reads it and its `derived_norms` by these rules (complete list):
  1. the `project.json` cannot be read when it does not exist, is not UTF-8, is not JSON, or its value is not a JSON object;
  2. its `derived_norms` meets [ORC-20](../../project-management/specs/module.md#where-the-repositories-are) when it is absent, or is a list whose every entry is a JSON object with a `type` of the form of ORC-20, no `type` twice in the list, and a `use_case` of the form `/<module>:<use case>`, where `<module>` and `<use case>` are each one or more lower-case ASCII letters, digits and `-`;
  3. such a script does not check that the use case of `use_case` exists in the marketplace: the step of layer 2 finds out when it runs it (NRM-2).

  Rationale: a `derived_norms` that names a type without a use case that could generate it is not the one by which the step of layer 2 runs the derived-norms generators, so neither the record of NRM-16 nor the comparison of NRM-11 may take its types; whether the use case exists depends on the plugins installed in a session, which a script that reads a commit cannot see.
- **NRM-2.** When `/norms-management:build` and `/norms-management:verify` succeed, the step of layer 2 (ORC-8) runs the derived-norms generator of each type in the order of NRM-1, with no question to the user, also when the build changed no norm. A derived-norms generator that stops with an error does not stop the next one. A check that fails (NRM-5) is no error of its generator.
- **NRM-3.** A derived-norms generator takes the norms only from `data/tree.jsonl`, `specs-repo-annotated/` and the versions of `data/tree.jsonl` in the history of the repository, and never reads a file of layer 1. Besides the norms it reads only (complete list): the output of its type; the output of a type listed before its own in `derived_norms` (NRM-1), when the spec of its derived-norms generator names that output; its own list before the run, from the history of the repository (NRM-13, NRM-15); the files of its own plugin; the record of the installed plugins of Claude Code and the git data of the checkout that holds its plugin (NRM-4); the issues of the repositories where it opens issues (NRM-7). Rationale: a generator that read layer 1 or any other file could derive what the norms of layer 2 do not say, and its output would no longer follow from them alone; it reads its own list before the run so that a derived norm keeps its derived norm ID across runs (NRM-13), and reads it from the history, never from the working tree, so that a list left half written by a stopped run gives no ID.
- **NRM-4.** A derived-norms generator writes in the repository only the output of its type.
- **NRM-5.** The first line of the status file is a JSON object with these fields, and with others only when the spec of its derived-norms generator names them (complete list of the fields every status file has):
  - `"type": "meta"`;
  - `"specs_commit"`: the commit of layer 1 that the meta line of `data/tree.jsonl` records;
  - `"generator"`: an object with exactly `"plugin"`, the name of the plugin of the derived-norms generator; `"version"`, the `version` of the plugin's `.claude-plugin/plugin.json`; and `"marketplace_commit"`, the commit of the marketplace that the plugin was installed from, as the spec of the derived-norms generator says how it is found, or `"none"`;
  - `"model"`: the exact model ID that ran the derived-norms generator;
  - one field `"<name>_sha256"` for each other file of the output, whose `<name>` the spec of the derived-norms generator gives, with the SHA-256 of that file; for the list of derived norms (NRM-12), `<name>` is `derived_norms`.

  Every plugin with a derived-norms generator has a `version` in its `plugin.json`.

  Rationale: the status file records from which norms, with which generator and version, and with which model the output was made, so that a later run knows what to derive again and a reader can tell an output that is behind; the SHA-256 of each other file of the output, the list of derived norms among them, lets the check (NRM-6) see a file that was changed after its generator wrote it.
- **NRM-6.** Each derived-norms generator has a check, which fails when its output does not follow from the current `data/tree.jsonl`, when NRM-5 does not hold, when its list of derived norms does not meet NRM-12 to NRM-14 (complete list: what NRM-12 says that the list alone shows, what NRM-12 to NRM-14 say of the list against the other files of its output, and what NRM-13 says of the list against its list before the run, which the generator reads from the history (NRM-3): that a derived norm that is the same as one of the list before the run keeps its derived norm ID, that a derived norm ID of the list before the run names no other derived norm, that no derived norm ID is given again, that new derived norm IDs follow the order of NRM-13, and that `last_derived_norm_number` does not decrease), or when its output holds a pending item. Rationale: layers 3 and 4 take the list of derived norms as it is, without reading the files of the output that it names (NRM-12), so a list whose derived norm IDs, lines, cited norms or derived norm fingerprints do not match the output would make them cite the wrong derived norm or miss a change; only the check of the generator knows the form of its output and can see it; and a derived norm ID that moved to another derived norm, or was given again, shows only against the list before the run, while every citation of layers 3 and 4 would then name what it was not written for (NRM-13).
- **NRM-7.** A derived-norms generator derives again only what a change of `data/tree.jsonl` calls for: an item whose norm changed, is new or is gone, and each part of the output that cites such a norm ([LAY-3](../../development-methodology/specs/layers.md#rules)). The one exception is a new version of the derived-norms generator: when the `version` of its plugin's `plugin.json` is not the `version` of `generator` in the status file of its type when the run starts (NRM-5), it derives again the whole output of its type, also when no norm changed. A derived norm that it derives again with the same content and the same cited norms, each with the same norm hash, keeps its derived norm fingerprint (NRM-14). Its list of derived norms is written again at every run, from the whole output (NRM-15), so the derived norm fingerprint of a derived norm whose citations it updated changes also when nothing else of the derived norm changed (NRM-14). Rationale: deriving everything again would change items whose norms did not change, and with them their derived norm fingerprints, so acceptance units and code that cite them would become stale for nothing; a new version is the exception because any item may be one that it fixes, and no change of the norms would reach that item ([LAY-3](../../development-methodology/specs/layers.md#rules), [LAY-6](../../development-methodology/specs/layers.md#rules)), and an item that it derives again unchanged keeps its derived norm fingerprint, so only what it changes makes acceptance units and code stale; the list is written again whole because a derived norm fingerprint depends on the norm hashes that the derived norm cites (NRM-14), and a list patched in part could keep a derived norm fingerprint that no longer matches, which layers 3 and 4 would not see.
- **NRM-8.** Each pending item gets its own issue in the repository of layer 1, opened at once by its derived-norms generator, with no question to the user ([LAY-5](../../development-methodology/specs/layers.md#rules)).
- **NRM-16.** After the last derived-norms generator, and before the commit of NRM-9, a script of the step of layer 2 writes the record of the types of derived norms, `specs-derived/types-of-derived-norms.json`, also when the project has no derived norms and when a derived-norms generator stopped with an error. It is in UTF-8 without a byte order mark and holds one line and nothing else: a JSON object, its `{` the first character of the file and its `}` followed only by one line feed (LF), with no other line feed and no carriage return; the object has exactly the field `"types_of_derived_norms"`: the `type` of each entry of `derived_norms` of the `project.json` by which the step ran the derived-norms generators (NRM-1, NRM-2), in their order, `[]` when there is none; each type in the form of [ORC-20](../../project-management/specs/module.md#where-the-repositories-are), lower-case ASCII letters, digits and `-`, and no type twice. A record meets NRM-16 when it holds all of that. Example (illustrative): `{"types_of_derived_norms": ["grammar", "semantics"]}`.

  The script is called with `--norms-repository <root>`, the root of the norms repository, and reads the `project.json` of its working tree. Its outputs, each line in UTF-8 and followed by one line feed (LF), which a check must match byte for byte (complete list):
  1. when it has written the record, it writes to its standard output the line `specs-derived/types-of-derived-norms.json`, and exits with status 0;
  2. when the `project.json` cannot be read, or its `derived_norms` does not meet ORC-20, both as NRM-1 says, or the file of the record cannot be written, it leaves the record that the working tree held before, unchanged or absent, writes to its standard error the line below, where `<reason>` is the first case that holds (complete list): `project.json cannot be read`; `derived_norms of project.json does not meet ORC-20`; `the file cannot be written`; and exits with status 1:

     ```text
     norms-management: the record of the types of derived norms is not written (NRM-16): <reason>
     ```

  3. when it is called without `--norms-repository`, or with another argument, it writes nothing, and exits with status 2 and the usage message of the module `argparse` of Python on its standard error.

  After the outcome 2, the step goes on (NRM-9), and NRM-11 takes the types of derived norms of its commit from the record that the commit holds, when it meets NRM-16, and otherwise from its `project.json`. Rationale: the step commits no `project.json`, which changes in commits of its own that `/project-management:sync` makes ([ORC-23](../../project-management/specs/module.md#where-the-repositories-are)), so the `project.json` of the commit before the last step need not be the one by which the last step ran; the record, committed with the output, tells NRM-11 which types the derived norms before had, and in which order.
- **NRM-9.** After the last derived-norms generator, the step of layer 2 makes one commit of every changed file of `data/`, `specs-repo-annotated/` and `specs-derived/`, each added by its path, never a folder, and pushes it to the default branch, also when a check failed. When nothing changed, it makes no commit. Its message names the commit of layer 1, the plugin and version of each derived-norms generator, the norms that changed and the issues opened.
- **NRM-10.** When the push is rejected, the step runs `git pull --no-rebase --no-edit` and pushes again, once. It never runs `git stash`, `git reset --hard`, `git clean` or `git pull --rebase`: other sessions may work in the same repository.
- **NRM-11.** The step ends with one report: the norms that changed by norm ID (`data/report.md`), and, for each type compared (rule 2 below), its derived-norms generator with its version, what it derived, the derived norms that changed, the issues it opened, the output of its check, and its error when it stopped with one. The derived norms that changed come from comparing the commit of layer 2 of the run (ORC-9) with the commit before the last step, by these rules (complete list):
  1. The commit of layer 2 of the run is compared also when the step made no commit, and then it is the head from before the step. When the step made a commit and then the pull of NRM-10, the commit of the step is compared, never the merge commit of that pull.
  2. The types compared are the types of derived norms of the commit of layer 2 of the run, in their order, then those of the commit before the last step that the first ones do not hold, in their order there. A commit of layer 2 of the run whose `project.json` cannot be read, or whose `derived_norms` does not meet [ORC-20](../../project-management/specs/module.md#where-the-repositories-are), both as NRM-1 says, when it holds no record of the types of derived norms that meets NRM-16, gives no comparison: the script names the reason and the run stops (ORC-10). A norms repository that is not a git repository, a commit that git does not find in it, and a commit of the walk along the first parents whose parents git cannot read also give no comparison. The words are those of rule 7.
  3. For each type compared, the list of derived norms (NRM-12) of the type at the commit of layer 2 of the run is compared with the list of the type at the commit before the last step, by derived norm ID: `new`, a derived norm ID that the list before did not hold; `changed`, one that both hold with two different derived norm fingerprints; `gone`, one that the list before held and the other does not.
  4. At the commit before the last step, these count as a list with no derived norm: the list of a type that is not one of its types of derived norms, a list that does not exist or does not meet NRM-12, and every list when there is no commit before the last step. The commit before the last step has no types of derived norms when it holds neither a record of the types of derived norms that meets NRM-16 nor a `project.json` that can be read with a `derived_norms` that meets ORC-20, both as NRM-1 says.
  5. At the commit of layer 2 of the run, the list of a type that is not one of its types of derived norms counts as a list with no derived norm, whatever the commit holds, so every derived norm of a type that `derived_norms` no longer names is `gone`. The list of one of its types that does not exist or does not meet NRM-12, as NRM-12 says of a list read alone, cannot be read; so cannot a list of one of its types that holds a derived norm behind its norms, which the script finds by comparing the `cited_norms` of each derived norm with `data/tree.jsonl` of the same commit, by the rules below the table of rule 7. The script names the type, the path of the list and the first thing of these that the list does not meet, in the words of rule 7, and the report shows it, so the run stops (ORC-10).
  6. The order of the types changed when two types that are types of derived norms of both commits are in one order at the commit before the last step and in the other at the commit of layer 2 of the run. The report then says so, with both orders (rule 7), and it is a change for ORC-10.
  7. The script of `/norms-management:build` that makes the comparison is called with `--norms-repository <root>`, the root of the norms repository, and `--commit <commit>`, the commit of layer 2 of the run. Its outputs, each line in UTF-8 and followed by one line feed (LF), which a check must match byte for byte (complete list):
     1. When it makes the comparison, it exits with status 0 and writes to its standard output these lines, in this order, and no other:
        1. when no type is compared, the line `no type of derived norms`;
        2. for each type compared, in their order, where `<label>` is the type, followed by ` (no longer in derived_norms)` when it is not one of the types of derived norms of the commit of layer 2 of the run (rule 5), the first case that holds:
           - when its list cannot be read (rule 5), the line `<label>: cannot be read: <path> at <commit>: <why>`, where `<path>` is the path of the list from the root of the norms repository, `<commit>` the commit of layer 2 of the run in its 40 lower-case hex digits, and `<why>` `it does not exist` when that commit holds no file at `<path>`, and otherwise the words of the first row of the table below that the list does not meet, or, when it meets every row, the words of the first case of the check against `data/tree.jsonl` below the table that holds;
           - when it has no derived norm `new`, `changed` or `gone` (rule 3), the line `<label>: no change`;
           - otherwise the line `<label>: <n> new, <c> changed, <g> gone`, the three counts in decimal, then, for `new`, `changed` and `gone` in this order, when at least one derived norm is in that state, the line of two spaces followed by `<state>: <IDs>`, where `<IDs>` are their derived norm IDs in the ascending order of their numbers, separated by `, `;
        3. when the order of the types changed (rule 6), the line `order of the types changed: <before> -> <now>`, where `<before>` are the types of derived norms of the commit before the last step and `<now>` those of the commit of layer 2 of the run, each in its order and separated by `, `;
        4. last, the line `derived norms cannot be read` when the list of a type compared cannot be read; otherwise `derived norms changed: yes` when a derived norm is `new`, `changed` or `gone`, or the order of the types changed; otherwise `derived norms changed: no`.
     2. When the commit of layer 2 of the run gives no comparison (rule 2), it writes nothing to its standard output, exits with status 1 and writes to its standard error the line below, where `<commit>` is the `--commit` as given when git finds no commit by it, and otherwise the 40 lower-case hex digits of the commit, and `<reason>` the first case that holds (complete list): `<root> is not a git repository`, where `<root>` is the absolute path of the root given; `it is not a commit of <root>`; `the parents of <commit of the walk> cannot be read`, in its 40 hex digits; `project.json cannot be read`; `derived_norms of project.json does not meet ORC-20`:

        ```text
        norms-management: the derived norms of <commit> of the norms repository cannot be compared (NRM-11): <reason>; the run stops after layer 2 (ORC-10)
        ```

     3. When it is called without `--norms-repository` or `--commit`, or with another argument, it writes nothing to its standard output, and exits with status 2 and the usage message of the module `argparse` of Python on its standard error.

     The script checks a list, as NRM-12 says of a list read alone, in the order of the rows of this table, and stops at the first row that the list does not meet; it reads every line as JSON (row 6) before any later row. In the words, `<n>` is the number of a line of the list, from 1; `<type>` the type of the list; `<ID>` the `derived_norm_id` of line `<n>`; rows 11 to 21 are checked for each line from line 2, in their order, all of them for one line before the next line; row 22 after every line (complete list):

     | Row | The list does not meet NRM-12 when | `<why>` |
     |---|---|---|
     | 1 | its bytes are not UTF-8 | `not UTF-8` |
     | 2 | it starts with a byte order mark (U+FEFF) | `a byte order mark` |
     | 3 | it is empty | `no meta line` |
     | 4 | its last character is not a line feed | `its last line is not followed by a line feed` |
     | 5 | it holds a carriage return (U+000D) | `a carriage return` |
     | 6 | line `<n>`, the first such line, is not one JSON text, `NaN`, `Infinity` and `-Infinity` not being JSON | `line <n>: not a JSON object` |
     | 7 | line 1 is not a JSON object with exactly the fields of the meta line, in their order, each once | `line 1: not the fields kind, type, last_derived_norm_number, in this order` |
     | 8 | its `kind` is not `"meta"` | `line 1: not the meta line` |
     | 9 | its `type` is not the type compared | `line 1: its type is not <type>` |
     | 10 | its `last_derived_norm_number` is not an integer 0 or greater; `true`, `false` and a number with a fraction or an exponent are none | `line 1: last_derived_norm_number is not an integer, 0 or greater` |
     | 11 | line `<n>` is not a JSON object with exactly the fields of a derived norm, in their order, each once | `line <n>: not the fields kind, derived_norm_id, derived_norm_fingerprint, name, path, first_line, last_line, cited_norms, in this order` |
     | 12 | its `kind` is not `"derived_norm"` | `line <n>: kind is not derived_norm` |
     | 13 | its `derived_norm_id` is not a string of the form `<type>:<number>` of NRM-13 | `line <n>: derived_norm_id is not a derived norm ID of <type> (NRM-13)` |
     | 14 | the number of its derived norm ID is not greater than that of the line before, when the line before is a derived norm | `line <n>: <ID> is not after the derived norm ID before it` |
     | 15 | the number of its derived norm ID is greater than `last_derived_norm_number` | `line <n>: <ID> is after last_derived_norm_number` |

     Example (binding): a list of the type `grammar` whose line 3 holds the derived norm ID `grammar:1` after `grammar:1` on line 2, at the commit `<commit>`, gives the line `grammar: cannot be read: specs-derived/grammar/derived-norms.jsonl at <commit>: line 3: grammar:1 is not after the derived norm ID before it`.

     A list of the commit of layer 2 of the run that meets every row of the table, and holds at least one derived norm, is then checked against `data/tree.jsonl` of that commit (rule 5), by these cases, in this order, the first that holds giving `<why>` (complete list):
     1. `data/tree.jsonl` does not exist at that commit, is not UTF-8, has a line that is not a JSON object, or has a line of `type` `node` whose `id` or `tree_hash` is not a string: `data/tree.jsonl cannot be read`;
     2. of the derived norms, in the order of their lines, and of the cited norms of each, in their order, the first cited norm whose `norm_id` is the `id` of no active node of `data/tree.jsonl`, a line of `type` `node` whose `status` is `active` or absent ([R61](norms-versions.md#data-and-outputs)); a line of `type` `node` with any other `status`, `retired` among them, holds no norm, since a retired node is no longer a norm: `line <n>: <ID> cites <norm ID>, which data/tree.jsonl does not hold`, where `<norm ID>` is that `norm_id`;

     The check of a list against `data/tree.jsonl` reads no file that `path` names. A list of the commit before the last step is never checked against `data/tree.jsonl` (rule 4).

     Example (binding): at the commit `<commit>`, a list of the type `grammar` whose line 2 is the derived norm `grammar:12` of NRM-12, while the line of `type` `node` of `data/tree.jsonl` whose `id` is `EXP-11` has a `tree_hash` that starts with `5a627175`, gives the line `grammar: cannot be read: specs-derived/grammar/derived-norms.jsonl at <commit>: line 2: grammar:12 cites EXP-11@e105eaa8, and the norm hash of EXP-11 in data/tree.jsonl is 5a627175`.

  The report shows the output of the script of rule 7 as it is, and ends with one line, by the first case of ORC-10 that holds, which a check must match byte for byte (complete list):
  1. when the script exited with status 1, or its last line is `derived norms cannot be read`: `The run stops after layer 2: the derived norms cannot be read (ORC-10).`;
  2. when `data/report.md` shows no change of norm and the last line of the script is `derived norms changed: no`: `The run ends after layer 2: no norm, no derived norm and no order of the types of derived norms changed (ORC-10).`;
  3. otherwise: `Layers 3 and 4 follow (ORC-10).`

  A script makes the comparison, not the model. These are the only rules of this comparison: every script that makes it, the one of `/norms-management:build` and the one with which the orchestrator decides ORC-10 ([WFO-13](../../workflow-orchestration/specs/module.md#start-and-control-a-run)), follows them, so that both decide ORC-10 the same way. Rationale: a run that resumes and builds again the same commit of layer 1 makes no commit, yet the derived norms that an earlier step of that commit changed must still reach layers 3 and 4, as the norms that changed do through `data/report.md` ([R63](norms-versions.md#data-and-outputs)); the head from before the step may then be a merge commit of the pull of that earlier step, or a commit that changed only `project.json`, and its first parent would hide the derived norms of that step, so the comparison goes back to the commit before the last step, along the first parents, which never meet a commit that a pull brought; it compares the commit of layer 2 of the run itself, not the last commit of a step, because layers 3 and 4 read the derived norms there (ORC-9). The merge commit of the pull of the step itself is never compared, since its first parent is the commit of the step and it would show only what the pull brought. A type that `derived_norms` no longer names keeps its output in the repository, since no generator writes it again (NRM-4), so only the types of derived norms tell that its derived norms are gone ([CIM-9](../../code-implementation/specs/module.md#implement-the-changed-norms)); and since `## Derived norms` of an acceptance unit follows the order of the types ([ACU-78](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository)), a new order calls for layer 3 even when no derived norm changed. A list before that cannot be read was the defect of an earlier step and must not hide the derived norms of this one; a list that cannot be read at the commit of layer 2 of the run leaves layers 3 and 4 no derived norm they could cite, and the check of its generator (NRM-6) reports the rest of what is wrong with it. A derived norm behind its norms keeps the derived norm fingerprint it had before its norm changed, since its generator, which stopped with an error (NRM-2) or wrote a wrong list, did not update its citation (NRM-14), and the step commits it all the same (NRM-9); layers 3 and 4 compare only derived norm fingerprints ([ACU-26](../../acceptance-management/specs/module.md#done-is-a-state-not-an-event), [CIM-9](../../code-implementation/specs/module.md#implement-the-changed-norms)), so only this check, against the norm hashes of the same commit, keeps them from taking it as current ([LAY-12](../../development-methodology/specs/layers.md#rules)).

## The list of derived norms

These clauses are part of the interface that every derived-norms generator
follows. They give each derived norm a derived norm ID and a derived norm fingerprint of its own, and
list them in one place, so that layers 3 and 4 cite each derived norm, and see
when it changes, without knowing its type
([LAY-12](../../development-methodology/specs/layers.md#rules)).

- **NRM-12.** Each derived-norms generator writes, in the output of its type, the list of derived norms: the file `specs-derived/<type>/derived-norms.jsonl`, in UTF-8 without a byte order mark, one JSON object per line, each line followed by one line feed (LF), and no other line.
  - Its first line, the meta line, has exactly these fields, in this order: `"kind": "meta"`; `"type"`, the `type` of its entry of `derived_norms` ([ORC-20](../../project-management/specs/module.md#where-the-repositories-are)); `"last_derived_norm_number"`, an integer, 0 or greater, the number of the latest derived norm ID ever given in the type (NRM-13).
  - Each other line is one derived norm of the output, with exactly these fields, in this order (complete list):
    - `"kind": "derived_norm"`;
    - `"derived_norm_id"`: its derived norm ID (NRM-13);
    - `"derived_norm_fingerprint"`: its derived norm fingerprint (NRM-14);
    - `"name"`: the name that the spec of its derived-norms generator gives it (NRM-15): a string with at least one character that is not a space or a tab, and with no control character (Unicode category Cc), no line separator (U+2028) and no paragraph separator (U+2029);
    - `"path"`: the path of the file of the output that holds it, from the root of the norms repository, its parts separated by `/`; never the list of derived norms, nor the status file;
    - `"first_line"` and `"last_line"`: the numbers, from 1, of the first and the last of its lines in that file, the file split into lines at each line feed; `first_line` is not greater than `last_line`, and its lines hold all its citation lines;
    - `"cited_norms"`: one object per norm that its citation lines cite, with exactly the fields `"norm_id"` and `"norm_hash"`, in this order, as its citation line gives them; at least one object; no norm ID twice; in the order of the norm IDs, compared code point by code point.
  - The lines of the derived norms are in the ascending order of the numbers of their derived norm IDs. No two of them have the same derived norm ID, and the lines of two derived norms of one file have no line in common.
  - A type whose output holds no derived norm has a list with its meta line only.
  - A list meets NRM-12 when it holds all that NRM-12 says that the list alone shows, read with no other file: its encoding and its lines, the fields of each line, their order and the form of their values, the order of the derived norm IDs, and that no two derived norms of one `path` share a line. A script of layer 3 or 4 checks only that; the comparison of NRM-11, in `/norms-management:build` and in the orchestrator, also checks that no derived norm of a list of the commit of layer 2 of the run is behind its norms (NRM-11, rule 5); none of them reads a file that `path` names to check it. What NRM-12 to NRM-14 say of the list against the other files of the output (that `path` names a file of the output that is not the status file, that the lines from `first_line` to `last_line` hold all the citation lines of the derived norm, that `cited_norms` is what they cite, and that `name` and `derived_norm_fingerprint` are those of NRM-15 and NRM-14), and what NRM-13 says of the list against the list before the run, only the check of its generator checks (NRM-6), which knows the form of that output.

  Binding example; what binds is the fields, their order, their nesting and the types of the values, not the values: the list of a type `grammar` whose grammar holds, at its lines 40 to 42, the rule `power` below, with the derived norm ID `grammar:12`, and whose latest derived norm ID given is `grammar:41`.

  ```text
  // EXP-11@e105eaa8: ^ is right-associative
  // EXP-8@a0b54578: the operators and their order
  power: unary ("^" power)?
  ```

  ```json
  {"kind": "meta", "type": "grammar", "last_derived_norm_number": 41}
  {"kind": "derived_norm", "derived_norm_id": "grammar:12", "derived_norm_fingerprint": "0ced57c3", "name": "power", "path": "specs-derived/grammar/clean.lark", "first_line": 40, "last_line": 42, "cited_norms": [{"norm_id": "EXP-11", "norm_hash": "e105eaa8"}, {"norm_id": "EXP-8", "norm_hash": "a0b54578"}]}
  ```

  Deliberate design: one file, of the same name and the same form for every type, beside the other files of the output. Rationale: a session of layer 3 or 4 reads the derived norms of every type, their derived norm IDs, their derived norm fingerprints, the norms they cite and their text, with one reader that knows no type ([ACU-78](../../acceptance-management/specs/module.md#the-files-of-the-acceptance-repository), [CIM-11](../../code-implementation/specs/module.md#the-derived-norms-of-the-code)); the status file stays the generator's own (NRM-5).

- **NRM-13.** The derived norm ID of a derived norm is `<type>:<n>`, where `<type>` is the `type` of its entry of `derived_norms`, and `<n>` a number from 1, without leading zeros. Example (illustrative): `grammar:12`. A norm ID never has this form, since it holds no `:` ([R61](norms-versions.md#data-and-outputs)).
  - A derived norm keeps its derived norm ID from one run of its derived-norms generator to the next while it is the same derived norm, as the spec of its generator says (NRM-15), even when its content, the norms it cites or its place in its file change.
  - A derived norm that is not the same as one of the list before the run gets the derived norm ID `<type>:<last_derived_norm_number + 1>`, the next one for each new derived norm, in the order of their place in the output: by `path`, compared code point by code point, then by `first_line`. The meta line then holds the number of the last one given.
  - A derived norm ID is never given again, even after its derived norm is gone. `last_derived_norm_number` never decreases, and is never lower than the number of a derived norm ID of the list. A type whose list does not exist yet starts from 0.

  Example (illustrative): with `last_derived_norm_number` 41, a run that adds the rules `call` and `index` of the grammar, in this order in the file, gives them `grammar:42` and `grammar:43`, and sets it to 43; a later run that removes `index` leaves it at 43, and the next new rule is `grammar:44`.

  Rationale: a derived norm is cited by its ID in layers 3 and 4 (ACU-56); an ID that moved to another derived norm would make a citation name what it was not written for, and only a number that only grows can tell which IDs were already given.

- **NRM-14.** The derived norm fingerprint of a derived norm is computed in these steps, in this order (complete list):
  1. the bytes of its file are decoded as UTF-8, each `\r\n` is replaced by `\n`, and the text is split into lines at each `\n`, which belongs to no line;
  2. its lines, from `first_line` to `last_line`, are taken, and every space (U+0020) and tab (U+0009) at the end of each of them is removed;
  3. its citation lines are removed; the lines that are left, without the empty lines at their start and at their end, are its content;
  4. the text to hash is, in this order: for each object of its `cited_norms`, in their order, `<norm ID>@<norm hash>` followed by one `\n`; then one `\n`; then each line of its content followed by one `\n`; all of it encoded as UTF-8;
  5. the derived norm fingerprint is the first 8 hex digits, in lower case, of the SHA-256 of those bytes.

  So the derived norm fingerprint changes when the norm hash of a norm it cites changes, when it cites another norm or one fewer, and when its content changes; it does not change when only the reasons of its citation lines, the order of those lines, the blanks at the end of a line or its place in its file change.

  Binding example; what binds is the derived norm fingerprint: the derived norm `grammar:12` of NRM-12 has the content `power: unary ("^" power)?`, the text to hash `EXP-11@e105eaa8\nEXP-8@a0b54578\n\npower: unary ("^" power)?\n`, and the derived norm fingerprint `0ced57c3`.

  Rationale: the norms that a derived norm cites, each with its norm hash, say what it was derived from, and its content says what it contributes; a derived norm fingerprint of both changes whenever either changes, so the acceptance units and the code that cite it become stale through it alone (LAY-12). The text of a norm hash never holds an empty line, so the empty line that follows the norms tells them apart from the content.

- **NRM-15.** The script of each derived-norms generator, never the model, gives the derived norm IDs, computes the derived norm fingerprints and writes the list of derived norms, from the files of the output that the generator wrote and from its list before the run; the script also checks them (NRM-6). The spec of each derived-norms generator states (complete list):
  - what one derived norm of its output is;
  - its name in the list of derived norms;
  - the form of its citation lines, after the comment mark of the language of its file;
  - what makes a derived norm of a run the same derived norm as one of the list before the run (NRM-13).

  Example (illustrative): a generator of a grammar may state that one derived norm is one rule or terminal of the grammar, with all its lines and the citation lines just above it; that its name is the name of the rule or terminal; and that a derived norm is the same as one of the list before the run when it has the same name.

  Every derived norm cites at least one norm ([LAY-3](../../development-methodology/specs/layers.md#rules)); the citation lines of a derived norm are its only lines that cite a norm.

  Rationale: a derived norm ID or a derived norm fingerprint that the model gave could differ from one run to the next for the same output, and then layers 3 and 4 would see a change where none happened; a script gives the same answer every time. Only the generator knows the form of its own output, so its spec says what one derived norm is and when two runs hold the same one; without that, NRM-13 and NRM-14 could not be applied to its output, and a citation line that the script did not recognize would leave a derived norm citing a norm that NRM-14 does not hash.
