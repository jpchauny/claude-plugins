# Clean derived norms

**Prefix:** CDN

**Audience:** The people who keep layer 2 of the Clean Language project; whoever builds a use case of the plugin `clean-derived-norms`

**Scope:** The derived norms of Clean, one use case per type, each a derived-norms generator of the interface of norms-management, [NRM-1 to NRM-11](../../../../indra-software-factory/modules/norms-management/specs/module.md#derive-the-derived-norms) and [NRM-12 to NRM-15](../../../../indra-software-factory/modules/norms-management/specs/module.md#the-list-of-derived-norms). What each type derives, and how, is in the spec of its use case. Out of scope: the norms, which `/norms-management:build` writes; the rules of the Clean examples, which are in [clean-examples](../../clean-examples/specs/module.md)

The module `clean-derived-norms` of the app Clean Language, listed in [app.md](../../../specs/app.md). It is installed in the repository of layer 2 of the project ([CLN-1](../../../specs/app.md#rules)).

## Terms

| Term | Meaning |
|---|---|
| Fragment | A norm of `data/tree.jsonl` of kind `code_block`, with status `active`, whose code block is a Clean example of [clean-examples](../../clean-examples/specs/module.md#terms): its info string is `clean-language`, or starts with `clean-language` followed by a space. |
| File line, path of a file line, file of a program, program | As [clean-examples](../../clean-examples/specs/module.md#terms) defines them, for the code of a fragment. |
| Module script | `scripts/derived_norms.py` of the plugin: the code that the scripts of the use cases of this module share (CDN-7). |
| Derived norm, derived norm ID, derived norm fingerprint | As [layers.md](../../../../indra-software-factory/modules/development-methodology/specs/layers.md#terms) defines them. |
| Acceptance unit behind layer 2 | As [acceptance-management](../../../../indra-software-factory/modules/acceptance-management/specs/module.md#terms) defines it. |
| List of derived norms, lines of a derived norm, citation line, content of a derived norm, list before the run, commit of layer 2 of the run | As [norms-management](../../../../indra-software-factory/modules/norms-management/specs/module.md#terms) defines them. |

## Rules

- **CDN-1.** Each use case of this module is the derived-norms generator of one type of the `derived_norms` of the project's `project.json`, and follows [NRM-1 to NRM-11](../../../../indra-software-factory/modules/norms-management/specs/module.md#derive-the-derived-norms) and [NRM-12 to NRM-15](../../../../indra-software-factory/modules/norms-management/specs/module.md#the-list-of-derived-norms). What one derived norm of its type is, the key of which CDN-10 makes its name, and the form of its citation lines are in the spec of the use case; what keeps a derived norm the same from one run to the next, its name, is the same for every use case and is in CDN-8 alone (NRM-15).
- **CDN-2.** A use case of this module takes the expected outcome of each fragment from its opening line, as [CEX-4 to CEX-7](../../clean-examples/specs/module.md#the-opening-line) state it, and its expected output only from its expected output block, as [CEX-27 to CEX-30](../../clean-examples/specs/module.md#the-expected-output) state it; never from a comment of its code.
- **CDN-3.** A fragment whose opening line is none of the forms of CEX-4 is a pending item of every use case of this module, and gets its issue in layer 1 ([NRM-8](../../../../indra-software-factory/modules/norms-management/specs/module.md#derive-the-derived-norms)).
- **CDN-4.** No use case of this module checks the rules of [CEX-20](../../clean-examples/specs/module.md#what-is-checked-and-by-whom), which the audit and the hook of `clean-examples` check in layers 0 and 1. Of the rules of [CEX-21](../../clean-examples/specs/module.md#what-is-checked-and-by-whom), the use cases of this module check these, and no other (complete list):
  - `derive-grammar`, the syntax: that each file of the program of a fragment with `expect=valid` or `expect=error` parses, and that the program of one with `expect=syntax-error` does not (its spec states where the parse may fail);
  - `derive-semantics`, the rest of CEX-5 and of CEX-7, CEX-29, and CEX-31: that a fragment with `expect=valid` gives no error code and, when it has an expected output block, writes exactly its expected output; that a fragment with `expect=error` gives exactly its error code, at build or at run time (its spec states how); and that a fragment that is not a whole program, outside the exception of CEX-31 for a fragment with `expect=error`, is pending, with the reason that it is not a whole program (CEX-31), and gets its issue in layer 1 as a defect of the example; a fragment that the exception covers is checked for its error code, as any fragment with `expect=error`. It does not check `expect=syntax-error`.
- **CDN-5.** A citation of a norm in the code of a use case of this module that becomes stale (its norm has another norm hash, is retired or is gone) gets its own issue in `jpchauny/claude-plugins`, the repository of this plugin, opened at once by the use case.
- **CDN-6.** A use case of this module reads the code of a fragment as its program: it splits the code into its files as [CEX-35](../../clean-examples/specs/module.md#the-files-of-a-program) says, from the file lines alone, and reads each file as a whole Clean source file, alone. The `<n>` of `line=<n>` counts the lines of the whole code ([CEX-6](../../clean-examples/specs/module.md#the-opening-line)), and a use case that compares a place in a file with it maps that place to the lines of the whole code (its spec states how). Splitting the files is no check of them: whether a path has the form of CEX-11, whether two files have one path (CEX-37), whether a code line stands before the first file line (CEX-36), which file holds `start:` (CEX-38) and whether `<n>` is a line of a file (CEX-39) are rules of CEX-20, which CDN-4 leaves to layers 0 and 1. Rationale: a program of several files is one example, and every generator of layer 2 must split it into the same files, the way the audit and the hook do, so that the grammar parses and the semantics runs the same program.
- **CDN-7.** The script of each use case of this module imports the module script, and no script of a use case imports the script of another use case ([DEV-7](../../../../../specs/development.md#levels)). The module script holds the code that the scripts of two use cases or more use (complete list): reading `data/tree.jsonl` and its norms; the fragments, their opening line, their case text and the files of their program (CDN-6); the citations in the code of a script, and their stale citations; the plugin, its version and its tooling commit, and the parts of a header line that every status file has, among them the version of the generator that the status file names, which tells a new version of the plugin ([NRM-7](../../../../indra-software-factory/modules/norms-management/specs/module.md#derive-the-derived-norms)); and the parser of the grammar, with its indenter, that parses the files of a program; and the list of derived norms of a type, which knows no type (NRM-12 to NRM-15): the lines of a file of the output as NRM-14 splits them, the name of a derived norm from the key of its item (CDN-10), the derived norm fingerprint (NRM-14) and the norms that the citation lines of a derived norm cite, from the lines of the derived norm and the citation form of its use case; the reading of the list before the run (CDN-9) and of the list in the working tree; the derived norm IDs (CDN-8); the writing of the list; and the check of the list against the derived norms of the output and against the list before the run. No script of the module compares two lists of derived norms to tell the derived norms new, changed and gone: the step of layer 2 does, as NRM-11 says ([DGR-15](../use-cases/derive-grammar/specs/derive-grammar.md#derive-the-grammar)). The code that one use case alone uses is in the folder of that use case. Rationale: the parser is in one place, so the semantics parses each fragment exactly as the check of the grammar does; the list of derived norms is in one place, so both types give the derived norm IDs, compute the derived norm fingerprints, and write and check their lists by the same code; and no use case depends on the files of another.
- **CDN-8.** The script of each use case of this module writes the list of derived norms of its type at each `seal`, from the whole output and the list before the run alone, as NRM-12 to NRM-15 say. A derived norm of the run is the same derived norm as one of the list before the run when both have the same name (CDN-10), and only then: this is what keeps a derived norm the same from one run to the next for every use case of this module (NRM-15), and the spec of no use case states it again; when several derived norms have one name, they pair in order: the k-th derived norm of that name in the run, in the order of NRM-13 (by `path`, then by `first_line`), keeps the k-th derived norm ID of that name in the list before the run, in the ascending order of their numbers; a derived norm of the run of that name beyond the count of those derived norm IDs is new, and a derived norm ID of that name beyond the count of derived norms of the run of that name is gone. So a run that changes nothing gives every derived norm its derived norm ID again, those of one name among them. The new derived norms get their derived norm IDs as NRM-13 says, in that order, after the greatest of the `last_derived_norm_number` of the list before the run and of the numbers of the derived norm IDs it holds, or after 0 when there is no list before the run (CDN-9). `seal` does not read the list in the working tree, which an earlier `seal` of the same run may have written: each `seal` gives every derived norm ID again from the list before the run, so a new derived norm may get from a later `seal` of the run another derived norm ID than an earlier `seal` gave it. Rationale: the deriver may seal several times in one run (after each file), and NRM-13 numbers the new derived norms in the order of their place in the whole output, which only the last `seal` sees; the step of layer 2 commits the list once, after the last generator (NRM-9), so no layer reads a derived norm ID that an earlier `seal` gave and a later one changed; only the list before the run tells which derived norm IDs layers 3 and 4 may already cite, and a derived norm that one `seal` drops and a later `seal` writes again gets back the derived norm ID it has there; pairing every derived norm ID of a name, and not only the lowest, keeps the derived norm IDs of two derived norms of one name from one run to the next, so a run that changes nothing reports no derived norm new or gone ([NRM-11](../../../../indra-software-factory/modules/norms-management/specs/module.md#derive-the-derived-norms)) and makes no acceptance unit behind layer 2.
- **CDN-9.** The module script reads the list before the run of a type from the history of the repository of layer 2, never from its working tree ([NRM-3](../../../../indra-software-factory/modules/norms-management/specs/module.md#derive-the-derived-norms)), at the head of its default branch: the branch that `refs/remotes/origin/HEAD` names, or, when the repository has no `refs/remotes/origin/HEAD`, the branch that `HEAD` names. There is no list before the run only when the commit at that head does not hold the list of the type, or when the repository has no commit yet; the type then starts from 0 (NRM-13). In every other case where the script cannot take that list from that commit, the list before the run cannot be read (complete list): git cannot run; the folder is not in a git work tree; `HEAD` names no branch and there is no `refs/remotes/origin/HEAD`; the default branch has no commit while the repository has one; or git fails to give the bytes of the list. A list before the run that cannot be read stops `seal`, which writes nothing and exits with 2, and the check reports it as a problem, as the spec of each use case says. Rationale: the step of layer 2 runs on the default branch and commits only after the last derived-norms generator ([NRM-9](../../../../indra-software-factory/modules/norms-management/specs/module.md#derive-the-derived-norms)), so during the step that head is the one of when the step started, as the term says; a list before the run taken as absent when it is only out of reach would number the derived norms from 0 and give derived norm IDs again, which NRM-13 forbids, so only a head that truly holds no list counts as none.
- **CDN-10.** The name of a derived norm in the list of derived norms is the key of its item, which the spec of its use case gives (a statement of the grammar, a declaration of the Lean code), with each character of the key that a name of [NRM-12](../../../../indra-software-factory/modules/norms-management/specs/module.md#the-list-of-derived-norms) may not hold, a control character (Unicode category Cc, the tab among them), a line separator (U+2028) or a paragraph separator (U+2029), replaced by one space. A key with none of them is the name as it is. Two keys that differ only in such characters give one name, and CDN-8 then tells which derived norm ID each of the two derived norms keeps. Example (illustrative): the directive whose first line is `%ignore<tab>WS` has the key `%ignore<tab>WS` and the name `%ignore WS`. Rationale: the key of a directive is its exact first line, and the key of a declaration with no name holds its first line, either of which may hold a tab, which NRM-12 forbids in a name; a name made so is never empty nor only blanks, since every key starts with a character that is neither a blank nor one of these, so `seal` never writes a list that its own check refuses, and the work list and the check still name each item by its exact key.
